# Contributing

Deployment harness for a 7 Days to Die dedicated server. Changes land through
CI, so the whole local gate is the whole contribution.

## Setup

`bash`, `make`, [`uv`](https://docs.astral.sh/uv/) and `shellcheck` on PATH.
Nothing else: `make` builds `.venv` from the hash-pinned
`requirements-lint.txt` with `uv`, and Python suites run under that venv.

```bash
make venv     # or let `make test` / `make lint` build it on first use
make help     # every target
```

## Before you push

```bash
make check    # lint then test, the same two commands CI runs
```

`make test-one SUITE=test_run_sh.py` runs a single suite while you iterate.
Full details of what each target covers: the README "Development" section.

## Branches and commits

One task, one branch off `main`, named `feat/`, `fix/`, `refactor/`, `docs/`,
`test/` or `chore/`. Commit messages say what changed and why, lowercase lead,
no "Fix:" prefix and no bullet-per-file dump. No AI attribution of any kind,
and no em dashes, in commits, PR text, code or docs.

## Pull requests

- `make check` green; CI runs the identical recipe.
- A user-visible change (image, config template, ops script, ports, scripts)
  gets a dated `## [X.Y.Z]` section in `CHANGELOG.md`; a release tag must
  match `VERSION` and have that section, both gated by
  `.github/workflows/release.yml`.
- Generated or runtime files (`data/`, `mods/`, `mods-available/`, `.env`,
  `backups/`) are never committed; they are host state, regenerated by
  `scripts/stage_mods.sh` and the container.
- New shell or Python scripts are picked up by the lint and test wildcards in
  the `Makefile`; no list needs updating.
- Secrets stay in `.env` or the environment, never in a commit or a log line.

## Adding a test

A Python suite is `scripts/test_<thing>.py`: import the shared reporter from
`scripts/harness.py` (`check(name, condition)` prints one line per pinned
behavior, `exit_status()` fails the run), then `make test-one
SUITE=test_<thing>.py`. Bash behavior goes into `scripts/test_lib_env.sh` or
the matching `scripts/test_<thing>.py` that drives a script through its real
entry point. Every non-trivial function needs a case; a case that would only
re-run the logic in the test is not a case.
